# 视觉主题与响应式布局阶段计划

状态：计划已确认，按 `color → BulrBackground → refactor_responsive_layout` 顺序执行。

本计划处理三个相互关联但必须分阶段完成的目标：统一主题色、增加动态模糊背景、重构运行时布局逻辑。每个目标使用独立工作分支完成，验证通过后在本地以 `--no-ff` 合并回 `main`，再开始下一阶段。

## 1. 冻结的产品行为

阶段开发不得改变以下已有行为：

- 日期记录、取消记录、未来日期阻断、历史统计、预测和导入导出协议；
- `compact`、`single`、`dual`、`scroll` 四种运行时的模式边界和页面组合；
- 日历滑动、年月跳转、历史列表排序、操作菜单展开/关闭和弹层关闭语义；
- 本地优先的数据保存方式，以及首次打开欢迎流程；
- 现有圆角、液态玻璃面板、菜单融合展开和启动 Loading 的结构。

视觉变化必须通过统一主题数据驱动，不能在组件中重新散落颜色常量或按设备复制主题实现。

## 2. 分支与合并顺序

| 阶段 | 工作分支 | 目标 | 合并门槛 |
| --- | --- | --- | --- |
| 1 | `color` | 统一主题色、四套主题、ActionMenu 内联切换 | 纯逻辑测试、ArkTS 构建、四种运行时启动检查 |
| 2 | `BulrBackground` | 主题色动态圆形背景与 `BlurStyle.Thin` 模糊层 | 构建、启动/旋转检查、动画不遮挡交互层 |
| 3 | `refactor_responsive_layout` | 按运行时分类优先重构布局度量计算 | 边界测试、四种模式和旋转检查、布局结果无回归 |

每个阶段执行以下固定流程：

1. 从最新 `main` 创建对应分支；
2. 只提交本阶段范围内的代码、测试和必要文档；
3. 执行构建和本阶段验证；
4. 切回 `main`，使用 `git merge --no-ff <branch>` 合并；
5. 在 `main` 上再次构建，确认合并后的状态，再创建下一分支。

## 3. 阶段一：`color`

### 目标

把所有运行时视觉色彩集中到一个主题定义文件，提供四套低饱和主题，并让用户在 ActionMenu 展开态中通过一行四个圆形色块直接切换主题，不打开额外窗口。

### 设计契约

主题 ID 固定为：

- `rose`：原生粉；
- `sage`：鼠尾草绿；
- `coral`：陶土珊瑚；
- `indigo`：靛蓝。

主题定义至少覆盖：页面背景渐变、主文字、次文字、强调色、经期标记色、选中态、玻璃面板底色、玻璃边框、遮罩色、占位边框、阴影色和 Loading 点色。组件只接收主题对象或主题 ID，不再声明同义的颜色常量。

主题状态由 `Index` 持有，默认 `rose`。主题选择写入本地 Preferences，读取失败或值不受支持时回退 `rose`。主题变化只刷新展示，不修改日期事实和导入状态。

ActionMenu 展开内容增加一行四个圆形主题按钮：

- 四个圆形按钮始终同时展示；
- 当前主题使用边框或外圈表示选中，不增加独立确认按钮；
- 点击颜色立即切换并保留菜单的当前展开状态；
- 主题行沿用当前菜单的液态玻璃背景、间距和展开动效；
- 菜单关闭、导入、导出、关于的现有回调保持不变。

### 主要改动边界

- 新增主题定义/解析模块，纯逻辑部分不依赖 ArkUI；
- `PreferencesStore` 增加主题的读取和保存协议；
- `Index` 增加主题状态和回调；
- `ResponsivePageShell`、日历、历史、ActionMenu、欢迎、导入、确认、关于和 Loading 组件改为消费主题；
- 将重复的玻璃面板颜色、文字颜色和页面背景移除；透明度数值也归入主题定义，避免主题切换后仍残留粉色玻璃。

### 验收

- 四个主题的所有页面主要色彩均来自统一定义；全仓生产代码不再出现旧主题的同义颜色常量；
- ActionMenu 中能在不打开新窗口的情况下切换四个主题，切换后页面立即更新；
- 重启后主题保持；损坏或未知主题值回退原生粉；
- 日期数据、弹层状态、菜单动作和四种运行时组合不变；
- `hvigorw test --no-daemon`、`assembleHap` 通过，并完成至少 compact、single、dual、scroll 的启动检查。

## 4. 阶段二：`BulrBackground`

### 目标

在页面背景层增加缓慢、不规则移动的主题色大圆形，并叠加 `BlurStyle.Thin`，形成不抢夺内容对比度的动态模糊背景。

### 设计契约

- 背景是独立层，位于页面内容之后，不参与 Scroll 内容高度；
- 大圆形使用当前主题的背景辅助色，至少保留两个不同大小和移动轨迹的形状；
- 运动缓慢、非同步、幅度受限，不能影响文字阅读和日期点击；
- `BlurStyle.Thin` 只用于背景模糊层，页面玻璃面板的既有模糊效果继续独立工作；
- 背景动画在页面隐藏时停止或不继续创建新的定时任务；
- `compact`、`single`、`dual`、`scroll` 使用同一背景组件，通过父容器尺寸适配，不复制四套动画。

### 主要改动边界

- 新增独立背景组件；
- 由 `ResponsivePageShell` 统一挂载背景层；
- 主题定义补充背景形状的颜色和透明度；
- 不把动画状态写入 `ResponsiveLayout`，不让背景组件参与运行时模式判定。

### 验收

- 四种运行时都能看到主题色缓慢移动和 `BlurStyle.Thin` 的模糊效果；
- 背景不覆盖操作菜单、日期点击、滚动和弹层遮罩；
- 页面切换、旋转和折叠后没有重复动画层或明显跳变；
- 构建通过，并通过模拟器截图/短时观察确认层级和视觉效果。

## 5. 阶段三：`refactor_responsive_layout`

### 目标

在不改变当前模式边界和视觉数值的前提下，把 `ResponsiveLayout.ets` 从“先计算大量通用值、再穿插模式条件”重构为“先分类运行时、再由对应模式配置生成指标”。

### 设计契约

1. 使用完整窗口宽高进行模式分类，安全区只参与内容可用空间和上下留白计算；
2. 保留当前模式边界：compact 优先检查分辨率与近方形比例，scroll 使用窄屏比例，single/dual 使用中间比例和分辨率条件；
3. `compact`、`single`、`dual`、`scroll` 分别拥有清晰的配置常量或配置函数；
4. 通用单位换算、`clamp`、比例计算和返回对象组装保持共享；
5. 组件只消费 `RuntimeLayoutMetrics`，不重新判断运行时、不复制布局断点；
6. 新增或调整一个模式参数时，能明确看到它影响的模式，避免修改一个视图意外改变另一个视图。

### 主要改动边界

- 先抽出模式分类结果和共享基础尺寸；
- 再将日历、历史、ActionMenu、页面顶部/底部间距按模式归组；
- 保留 `RuntimeLayoutMetrics` 字段名，除非证明字段是无调用方的死字段；
- 扩展边界测试，覆盖设备基线、旋转、Mate X7 横竖方向、compact 分辨率优先和大于 1.8 的横置约束；
- 不在本阶段调整视觉数值，视觉改动必须另开明确阶段。

### 验收

- 现有设备分辨率和旋转结果与重构前一致；
- 四种模式的每个组件仍读取同一份运行时指标，单元测试覆盖模式边界和关键尺寸；
- ArkTS 构建和纯逻辑测试通过；
- 在 Pura X Max、Pura X、Mate X7、MatePad/电脑比例和 Pura 90 基线下完成启动或窗口切换检查；
- `ResponsiveLayout.ets` 中不再出现难以追踪的跨模式嵌套条件，模式配置责任可直接定位。

## 6. 风险与停止条件

- 若 ArkUI 的主题色或模糊 API 在当前 SDK 上不支持，先保留纯色降级路径并记录具体 API/SDK 证据，不伪造动态效果已完成；
- 若主题切换导致玻璃面板文字对比度不足，优先调整主题定义，不在每个组件中添加主题特例；
- 若布局重构暴露当前测试断言与实现不一致，先区分“旧断言错误”和“行为回归”，不得用放宽断言掩盖回归；
- 任一阶段验证失败时，停留在当前分支修复，不提前创建或合并下一阶段分支。
