# 需求意图与细节审查

## 1. 意图保持情况

以下核心意图被完整保留：纯鸿蒙原生、离线隐私、快速记录任意经期日、日历为主界面、向下查看历史、低饱和粉色视觉、导入导出和下一次经期估算。

以下地方做了必要的产品化收敛：

- “一个界面”解释为一个 UIAbility/入口页面，而不是把所有内容挤在同一屏；仍然通过纵向分页保持单一主流程。
- “横向柱状图”落实为无边框的水平条形记录：日期是左侧行标签，柱条长度表示持续时长，持续天数只显示在每条柱的末端，不绘制持续天数坐标轴。
- “点击日期标记”落实为任意可见日期均可操作；再次点击立即撤销，不增加确认弹窗，保持记录动作连续。
- “不使用标准日历模板”落实为自绘 7 列网格、横向月份分页和自绘年/月跳转面板。
- 平板与宽折叠屏展开态通过最大内容宽度和紧凑行高适配，不让日历卡片按屏幕宽度无限拉伸。
- “最后一次持续到当日”落实为最后一个已记录起点统计到今天，最短为 1 天，并标注“进行中”；不替用户猜测尚未记录的日期。

## 2. 发现的技术细节错误或风险

### 风险 A：任意文本不等于任意语言理解

本地 ArkTS 应用可以可靠地解析预定义日期格式，但无法承诺识别所有自然语言、截图、表格和上下文。方案因此把首版定义为“规则解析 + 候选预览 + 用户确认”，而不是未经验证地承诺“自带小 AI”。

### 风险 B：把 CalendarPicker 当成完整月历主界面

系统日期选择器更适合选择日期或日期范围，未必能满足每个日期的经期状态、渐变背景和完整视觉定制。首版固定使用自定义 7 列网格，不把系统日历组件作为替代方案；系统能力只用于文件选择和必要的系统级授权流程。

### 风险 C：用 Scroll 实现整页分页可能停在半页

用户要求一次手势直达下一展示页，语义更接近 `Swiper`。技术设计优先使用纵向 Swiper；如果当前 SDK 的纵向能力或交互细节不满足，再用等高 Scroll + snap 作为备选，并以真机手势测试作决定。

### 风险 D：预测样本不足时伪造确定性

一个记录起点无法计算周期，两个起始日只能得到一个间隔，均不适合显示稳定预测。因此当前至少需要 3 个已完成记录段，并使用“左右/估算”措辞；当前实现不显示尚未实现的预测区间。

### 风险 E：本地隐私不等于不需要隐私说明

经期数据属于敏感健康相关数据。即使应用不联网，也要向用户清楚说明本地保存、导入导出、删除和系统备份边界，并在上架前完成适用地区的合规审核。

## 3. 未决但必须显式记录的产品选择

- 历史日期是否允许在日历上直接编辑。当前首版允许编辑当前月及可见相邻月份的日期，后续再评估是否开放更远日期的专门编辑入口。
- 记录日期的含义是否始终是经期首日。当前按“每个记录日都是一个起点”计算下一次起点间隔，适合只记录首日的工作流；如果用户记录的是连续每天，统计结果会被解释为多个起点，导入说明必须明确这一点。
- 是否需要提醒。原始需求未提出提醒，且提醒会引入通知权限和更复杂的隐私/生命周期行为，首版不做。
- 是否支持导入图片、截图和 OCR。原始需求只明确文本和 JSON；图片/OCR 另立需求，不在“任意文本”中偷渡。

## 4. 审查结论

方案没有把项目扩展成健康管理平台，也没有把“AI 解析”或云能力当成核心依赖。可执行的最小闭环是：本地每日标记 → 派生经期统计 → 透明估算 → 用户确认的导入导出。只有这条链在真机上稳定后，才考虑端侧 AI、历史编辑或更多健康字段。
