# 月迹技术设计

## 1. 技术基线

- 语言：ArkTS。
- UI：ArkUI 声明式 UI。
- 应用模型：Stage 模型，单个 UIAbility。
- 构建：DevEco Studio + Hvigor，使用工程内锁定的 HarmonyOS SDK。
- 持久化：首版使用 User Preferences（当前 SDK 对应的 ArkData API）键值型持久化，将小规模、版本化的领域 JSON 存在应用沙箱；暂不引入关系型数据库。
- 文件：通过 Core File Kit 的用户文件选择/保存能力读取或写入用户明确选择的文件。
- 图表：使用 ArkUI 基础布局自绘水平柱状记录，不使用网络图表库、Canvas 或 WebView。
- 网络：不声明网络权限，不引入 HMS、分析、推送、远程配置和云同步 SDK。

## 2. 模块边界

当前继续使用单模块，目录按职责分层，避免拆成多个 HAR/HSP。第一轮基础组件已经从 `Index.ets` 拆出，后续只在页面壳中增加多设备组合：

```text
entry/src/main/ets/
├── entryability/          # UIAbility 生命周期与窗口入口
├── pages/                  # 页面级容器，负责组装两个展示页
├── components/             # Calendar, History, ActionMenu, Welcome, Loading, About, Import
├── domain/                 # 日期、经期分组、统计与预测的纯业务逻辑
├── data/                   # PreferencesStore、导入导出 DTO、迁移
└── parser/                 # JSON 校验；文本/OCR 暂缓
```

当前 `pages/Index.ets` 负责页面状态、Preferences 和导入流程编排；`components/CalendarComponent.ets`、`HistoryComponent.ets`、`ActionMenuComponent.ets`、`WelcomeComponent.ets`、`LoadingComponent.ets`、`AboutComponent.ets`、`TextImportComponent.ets` 与 `ImportConfirmationComponent.ets` 已替换原有内联视图。组件只通过带默认值的 `@Prop` 和回调接收状态，不直接读写 Preferences；导入解析也不直接修改状态，必须经过预览确认动作。

## 2.1 响应式布局与组件边界

多设备适配不按设备型号复制页面，而按窗口可用宽度、窗口高度、横竖方向和折叠窗口状态选择布局组合。ArkUI 官方提供 `GridRow`/`GridCol` 断点布局能力，也支持通过窗口属性获取实际窗口尺寸；月迹应把这些能力限制在页面壳，不让业务组件知道设备型号。

布局模式先定义为三种：

| 模式 | 触发条件 | 内容组合 |
| --- | --- | --- |
| `compact` | 小方形或窄窗口 | 只保留核心月历，Pura X 折叠态不展示 logo |
| `single` | 竖向手机、直板屏和不适合并列的展开窗口 | 月历页与历史页继续使用纵向整页切换 |
| `dual` | Pura X 展开横向以及宽度足够的展开窗口 | 左侧月历、右侧历史统计；两块内容共享同一状态，不复制数据源 |

`dual` 不是简单把当前两个 `Swiper` 横向排列。横向双排时，页面应使用一个外层布局壳承载两个功能组件，取消纵向整页手势，保留月历内部横向换月手势，并让右侧历史统计在自身区域独立滚动；窗口变窄后再恢复 `single` 的纵向分页。

推荐的组件职责如下：

```text
Index / PageState
  └─ ResponsivePageShell     # 读取窗口度量，选择 compact/single/dual
      ├─ CalendarPage         # 月份、日期网格、年/月面板和日期事件
      └─ HistoryPage          # 预测、历史柱图、导入导出事件
```

拆分原则：

1. 先抽不依赖设备的 `CalendarPage`、`MonthJumpPanel`、`HistoryPage`、`HistoryChart` 和设计 token。
2. 组件通过 `@Prop`/`@Link` 或明确回调接收状态，不在组件内部加载 Preferences。
3. `ResponsivePageShell` 只负责布局组合、间距和手势策略，不重新实现日期或导入逻辑。
4. 先在当前 `single` 布局中替换组件并通过截图/交互回归，再实现 `dual`。
5. 每个组件提供可独立预览的默认属性，避免 DevEco 预览器出现本地初始化属性缺省错误。

窗口尺寸应在页面可见阶段读取；发生窗口旋转、折叠状态变化或避让区变化时更新度量。布局断点使用 `vp` 和容器宽度表达，五个指定画布只作为验收样本，不把像素坐标写死进业务组件。

## 3. 领域模型

日期统一使用本地日历的 `YYYY-MM-DD` 字符串作为业务键，不保存带时区的 ISO 时间戳来表示经期日，避免午夜跨时区导致日期漂移。

```ts
interface MenstrualDay {
  date: string;
  source: 'manual' | 'import';
}

interface HerculaDataFile {
  schemaVersion: 1;
  exportedAt: string;
  days: MenstrualDay[];
}
```

这里刻意把每日标记作为唯一事实来源：经期区间、持续天数、历史图表和预测全部由日期集合派生，不保存容易互相矛盾的冗余 `startDate/endDate/duration`。

派生规则：

1. 对日期按本地日期升序、去重。
2. 每个已记录日期都作为一个经期起点；下一条已记录日期存在时，本条时长为两起点之间的日期差。
3. 最后一条记录没有下一起点时，时长统计到今天，`durationDays = today - startDate + 1`，最短为 1 天。
4. 最后一条记录显示“进行中”。这意味着用户只记录经期首日时，周期长度可直接由下一次首日派生；漏记首日会影响统计结果，不能由系统静默补猜。
5. 所有日期解析、排序和差值计算必须使用明确的本地日期函数，不依赖浏览器日期解析的实现差异。

## 4. 记录与状态流转

```text
无日期标记 ──点击任意可见日期──> 日期已标记
日期已标记 ──再次点击同一日期──> 立即撤销
首次打开 ──欢迎弹窗动作──> 记录或导入
应用重新打开 ──读取 Preferences──> 恢复所有标记
导入候选 ──用户确认──> 合并、去重、持久化
导入候选 ──取消/解析失败──> 丢弃候选，不改变现有数据
```

导入合并使用 `Set<YYYY-MM-DD>` 的等价逻辑；排序后写回稳定 JSON，保证相同输入产生相同文件内容，便于备份比对。

## 5. 预测算法

首版只做透明、可解释的统计估算：

- 只有至少 3 个已完成经期段时才给出预测。
- 使用已完成记录的起始日计算相邻周期长度，并以中位数作为典型周期长度。
- `predictedStart = lastCompletedStart + medianCycleLength`。
- 当前 UI 使用单一“某年某月某日左右”文案，不显示尚未实现的预测区间。
- 不预测排卵、不推断怀孕、不提供医学建议。展示“根据已记录历史的估算”，并提供“仅供记录参考”说明。

如果最近一段仍在进行，当前实现将其排除在“已完成”样本之外，预测基于最近的已完成记录；UI 在样本不足时显示继续记录提示，避免把当前段误认为完整样本。

## 6. 导入解析

目标解析器按优先级处理：

1. JSON：验证 `schemaVersion`、`days[].date` 和枚举值；不符合 schema 时给出结构化错误。
2. 简单文本日期：识别明确的年月日分隔符，转换为 JSON 候选后进入预览确认。
3. 图片 OCR 导入：暂缓，不进入当前版本实现。

不做隐式联网请求，不把系统 AI 或云端模型当成首版必需依赖。当前导入的唯一数据契约是 `docs/json_SPEC.md`；简单文本只作为一种输入形式，必须先转换为 schema 候选并经过用户确认。OCR 和 AI 等待后续重新立项。

简单文本解析规则：

- 支持 `YYYY-MM-DD`、`YYYY/MM/DD`、`YYYY.MM.DD`、`YYYY年MM月DD日` 及同一行中使用空格、制表符或逗号分隔的明确年月日。
- 支持一段文本中按换行、分号或逗号列出多个日期；每个候选保留原文片段和解析结果。
- 不猜测缺失年份、月日顺序或自然语言语义；两位年份、无年份日期和无法确认的数字组合进入失败列表。
- 解析成功的候选统一生成 `days[].date`，`source` 使用 `import`，再复用 JSON 导入的未来日期过滤、去重、预览和确认流程。

## 7. 文件与隐私边界

- 读取导入文件：调用系统文件选择器获取用户授权 URI，再通过文件 API 读取；不遍历公共目录，不申请“全盘访问”。
- 保存导出文件：调用系统保存能力，由用户选择目标位置；不后台写入用户公共目录。
- 应用内部数据：只写应用沙箱；首版不接入备份云同步能力，是否允许系统级备份要在发布前根据隐私策略明确验证。
- 不记录原始导入文本日志，不向日志输出日期内容。
- 受敏感健康信息属性影响，发布前准备独立、易访问的隐私政策，说明本地处理范围、导入导出行为、删除方式和联系方式。

## 8. UI 组件选择

| 需求 | 首选实现 | 选择理由 |
| --- | --- | --- |
| 两个整页展示页 | 外层 `Swiper` 纵向分页 | 语义上就是整页切换，避免自由滚动停在半页 |
| 月历月份切换 | 自绘 `Stack` + `PanGesture` + `translate` | 当前实现承载前月、当前月、后月三个自绘页面，拖动时显示目标月份，松手后更新月份 |
| 月历主体 | `Grid`/`ForEach` 自定义 7 列网格 | 不使用标准 Calendar 模板；不显示星期标题和月份箭头，可完全控制标记色、圆角和触控目标 |
| 年/月跳转 | 自绘 `Grid` 选择面板 | 点击年/月控件展开候选项，避免引入标准日历外观 |
| 历史图表 | `Column` + `Row` 横向柱条布局 | 无第三方依赖；日期作行标签，时长显示在柱条末端，不需要坐标轴 |
| 导入文件 | DocumentViewPicker / 系统文件选择能力 | 当前只接受 JSON；用户主动授权，适配公共文件 URI |
| 导出文件 | 系统保存文件能力 | 不需要目录权限，符合本地隐私边界 |
| 小规模持久化 | User Preferences（ArkData） | API 简单，足以承载几十年每日记录 |
| 弹窗确认 | ArkUI 原生 Dialog/Sheet | 处理撤销、导入预览和错误反馈 |

页面布局约束：日历卡片设置 `maxWidth: 720vp`，日格保持固定触控尺寸，外层内容在宽屏居中；日历分页保持紧凑的 6 行高度。`single` 模式下外层纵向分页与内层横向分页只在各自方向响应手势；`dual` 模式取消两个功能区之间的纵向整页分页，保留月历内部横向分页，避免横向换月误触发页面切换。

使用的具体方法名、Kit 导入路径和 API 版本以创建工程时安装的 SDK API Reference 为准；禁止复制旧版 `@ohos.*` 示例而不经过当前 SDK 编译验证。

## 9. 测试策略

- 领域单元测试：日期排序、闰年、跨月、跨年、重复日期、记录起点间隔、未来日期、当前进行中、预测样本不足和异常周期。
- 解析测试：JSON schema 版本、非法日期、重复日期、未来日期、未知字段和超大文件；文本测试覆盖各种分隔符、混合文本、缺失年份、两位年份和部分失败；OCR 暂缓。
- UI 测试：点击任意日期、二次点击立即撤销、首次欢迎弹窗、年/月跳转、横向换月、纵向整页切换、空状态、动态柱高、字体放大、深色模式和无障碍朗读。
- 设备测试：优先使用 DevEco 模拟器验证文件 URI 授权、保存、应用重启恢复、平板和宽折叠屏展开态、横竖屏/多窗口适配；真机仅在模拟器无法覆盖或发布前补充低内存和系统授权行为。
- 隐私检查：发布包不含网络权限、不含第三方 SDK，不向日志输出经期日期。
